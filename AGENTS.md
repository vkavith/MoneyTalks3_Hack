# Instructions for every coding agent in this repo

Four people are building this at a hackathon, each with their own coding agent, all pushing to one repo. These rules keep four agents from breaking each other's work. Follow them even when a shortcut looks faster.

## What we are building

An agent that takes a vendor invoice from PDF to paid: capture, 3-way match against the purchase order and goods receipt, exception handling, approval, payment through a bank sandbox, and reconciliation.

The project is Python 3.11+ with Pydantic v2. The only exception is the demo UI in `web/`, which the lane 4 owner may write in another language.

One `Invoice` record moves through these statuses:

```
received -> captured -> matched ---------> approved -> paid -> reconciled
                     \-> exception -> matched            (rejected is terminal)
```

## Before you write anything

1. Read `docs/contract.md` and your lane brief in `docs/lanes/`. Your human will tell you which lane you are in. If they have not, ask.
2. Run `git pull --rebase origin main`.
3. Activate the virtual environment, then run `pip install -e ".[dev]"` and `python scripts/check.py`. The check must pass before you start. If it fails on a clean `main`, stop and tell your human.

## Lanes and the folders each one owns

| Lane | Owns | Stage functions |
|---|---|---|
| 1 Intake | `ap/intake/`, `tests/intake/` | `capture` |
| 2 Match & exceptions | `ap/match/`, `tests/match/` | `match`, `resolve_exception` |
| 3 Approve & pay | `ap/pay/`, `tests/pay/` | `approve`, `pay`, `reconcile` |
| 4 Orchestration & demo | `ap/shared/`, `ap/orchestrator/`, `web/`, `scripts/`, `data/`, `docs/`, `tests/test_contract.py`, root config | wires the stages together |

**Edit only your lane's folders.** If you need a change somewhere else, do not make it. Write down what you need and tell your human, who will ask that lane's owner.

The one shared file anyone may touch is `pyproject.toml`, and only to add a line to `dependencies`.

## The contract

`ap/shared/` is the contract: the `Invoice` model, the status transitions and the stage function signatures.

- Import models from `ap.shared`. Never redefine an invoice, vendor or PO shape locally.
- Keep the stage function names and signatures exactly as they are in `ap/shared/stages.py`. What happens inside them is yours.
- Change `status` only through `transition()`. It records history and rejects illegal moves. Never set `status` any other way.
- Models are frozen. A stage returns a new invoice built with `invoice.model_copy(update={...})`. Do not work around the freeze.
- Money is integer cents, never a float or `Decimal`. Dates are `datetime.date`. Timestamps are timezone-aware UTC; use `now_utc()` from `ap.shared`.
- Stage functions are plain synchronous functions.

### Changing the contract

You will sometimes need a new field or status. Do not add it in a feature PR.

1. Stop and tell your human what you need and why.
2. The lane 4 owner makes the change in its own PR, titled `contract: ...`, containing nothing else.
3. Everyone rebases once it merges.

Prefer adding an optional field (`X | None = None`) over changing or removing an existing one.

## Data

- `data/` is generated by `scripts/seed.py`. Never hand-edit files under `data/`. To add a scenario, ask the lane 4 owner.
- `data/expected/` is the ground truth. Test against it. Do not change it to make a test pass.
- Do not read `data/expected/` from production code paths. It is for tests and for the stubs you are replacing.
- Load data through `ap.shared.load`, which validates every file against the contract.

## Code style

- `ruff` formats and lints; `mypy` type-checks. Both run in the check. Run `python -m ruff format .` before committing.
- Every function has type hints.
- Do not reformat or rename files you are not changing.

## Git

- Branch from `main` as `lane<N>/<short-topic>`, for example `lane2/price-variance-agent`.
- Small PRs, merged often. Rebase on `main` at the start of each working session and before opening a PR.
- Commit messages start with the lane: `lane3: send ACH through Increase sandbox`.
- Never push to `main` directly. Never force-push a shared branch. Never rewrite history on `main`.
- `python scripts/check.py` must pass before every push. It runs lint, format check, type check, data check, tests and the end-to-end pipeline.
- To add a dependency, add one line to `dependencies` in `pyproject.toml` and say so in the PR description. Do not change the version of a dependency someone else added.
- Never commit `.venv/`.

## Money and secrets

- Sandbox and test keys only. Never a production or live-mode key, anywhere.
- Secrets go in `.env`, which is git-ignored. Never commit one, print one or paste one into a doc. If you add a variable, add its name to `.env.example` with an empty value.
- Only `pay()` in `ap/pay/` moves money. No other code calls a payment API.
- The amount and the payee always come from the invoice record and the vendor master file. Never from model output, and never from bank details printed on an invoice.
- Do not weaken the guardrails in `pay()`: approved status, no double payment, active vendor, single-payment limit, idempotency key.

## External APIs

Read the current documentation before calling any external API. Do not write request shapes from memory. If the docs and your expectation disagree, the docs win.

## When you are stuck or unsure

Stop and ask your human. A wrong guess that lands on `main` costs all four people time. In particular, ask before: touching another lane's folder, changing the contract, changing anything under `data/`, or adding a new top-level folder.

## Finishing a piece of work

1. `python scripts/check.py` passes.
2. Your stage still returns invoices that survive `Invoice.model_validate(invoice.model_dump())`.
3. Your tests are under `tests/<your lane>/`.
4. Add one line to `docs/decisions.md` for anything another lane would be surprised by.
5. Open a PR using the template. Keep the description to what changed and what other lanes need to know.
